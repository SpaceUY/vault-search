# vault-search: design

Status: POC. Self-contained module that ships as the `vault-search` skill (`.claude/skills/vault-search/`), so it can be copied into another vault unchanged. The vault supplies only its config (`.vault-search/config.json`) and one `include` line in its `Makefile`; see `SKILL.md` for the setup steps.

## Problem

`Manifest.md` is regenerated by an LLM skill. The output is large and non-deterministic, so every regeneration touches most of the file and causes merge conflicts. We also want a path to better retrieval (keyword search, later embeddings) without redesigning anything when the vault grows.

## Goals

- Remove manifest merge conflicts: the manifest becomes a local, gitignored, deterministic artifact.
- Provide a small CLI that Claude (or a person) calls to search the vault.
- Keep retrieval strategies pluggable. Using only the manifest, only FTS, or a later embeddings adapter must be a config change, not a code change.
- Work on any markdown vault with optional YAML frontmatter, not only this one.

## Non-goals (POC)

- Embeddings adapter (the interface leaves room for it, nothing more).
- CI and publishing to npm.
- Chunk-level indexing. The unit of retrieval is the note.

## Layout

```
.claude/skills/vault-search/    the skill: tool, docs and make targets (committed)
  SKILL.md                      how to use it and how to set it up in another vault
  DESIGN.md
  vault-search.mk               make targets, included from the vault's root Makefile
  package.json
  tsconfig.json
  src/
    cli.ts                    argument parsing, output formatting
    config.ts                 load and validate the vault's config file
    types.ts                  Doc, Hit, Strategy, SearchOpts, Ctx
    compare.ts                code-unit string comparison for deterministic ordering
    vault-reader.ts           walk markdown files, parse frontmatter, produce Doc[]
    registry.ts               strategy name to factory
    strategies/
      manifest.ts
      fts.ts
  test/
    fixtures/vault/           small synthetic vault
    helpers.ts                shared test builders
    *.test.ts

.vault-search/                  lives in the vault root, not in the skill
  config.json                   enabled strategies, vault root, ignore list (committed)
  .index/                       generated, gitignored (SQLite file lives here)
```

## Runtime and tooling

- Node 22.18 or later (the first 22.x release with unflagged type stripping). `node:sqlite` provides SQLite with FTS5, so there is no native dependency. Node strips TypeScript types natively, so there is no build step. `tsc --noEmit` is the typecheck.
- One runtime dependency: a YAML parser for frontmatter.
- TypeScript strict, no `any`, named exports, early returns, small single-purpose functions.
- `pnpm` for installs and scripts. Tests use `node:test`.
- The experimental-feature warning from `node:sqlite` is suppressed in the CLI entry point.

## Core types

```ts
interface Doc {
  path: string;          // vault-root-relative, forward slashes, includes .md
  title: string;         // first H1, else filename without extension
  description: string;   // frontmatter description, else empty string
  tags: string[];
  status: string | null;
  headings: string[];
  body: string;          // markdown without frontmatter
  hash: string;          // sha256 of file contents
}

interface Hit {
  path: string;
  title: string;
  description: string;
  score: number;         // higher is better, strategy-defined scale
}

interface SearchOpts {
  limit: number;
  pathPrefix?: string;
}

interface Ctx {
  vaultRoot: string;
  indexDir: string;
}

interface Strategy {
  name: string;
  build(docs: Doc[], ctx: Ctx): Promise<void>;
  search?(query: string, opts: SearchOpts, ctx: Ctx): Promise<Hit[]>;
  list?(opts: ListOpts, ctx: Ctx): Promise<ListEntry[]>;  // ListOpts { pathPrefix?, limit? }, ListEntry { path, title, description }
}
```

`search` and `list` are optional on purpose: a strategy can be build-only.

## Components

1. **VaultReader.** Walks the vault, skips the configured ignore list, parses frontmatter and headings, and returns `Doc[]`. It knows nothing about strategies. Unparseable frontmatter yields a Doc with empty metadata and a warning on stderr; it never aborts the run.
2. **Registry.** Maps strategy names from config to factories. Adding a strategy is one new file plus one registry line.
3. **Config.** `.vault-search/config.json` in the vault root (read from the current directory by default, or from `--config <file>`; the index is stored beside it):
   ```json
   {
     "vaultRoot": "..",
     "ignore": [".obsidian", ".git", ".claude", "Images", "node_modules", "Manifest.md", "README.md", "CLAUDE.md"],
     "strategies": ["manifest", "fts"]
   }
   ```
   Unknown strategy names fail fast with a clear message. `vaultRoot` is relative to the config file. Each `ignore` entry is a vault-relative path that matches a file or a folder (and everything under it). `Manifest.md` is ignored so the generated manifest is never indexed back into search results, and `README.md` and `CLAUDE.md` are ignored to match what the old manifest left out. Independently of this list, the reader always skips any file or folder whose name starts with a dot (the way Obsidian does), so tool and working directories such as `.superpowers` or `.github` are never indexed. Frontmatter with duplicate keys is accepted (the last value wins), as Obsidian accepts it.
4. **CLI.** Below, `search` stands for `node --disable-warning=ExperimentalWarning .claude/skills/vault-search/src/cli.ts`; day to day, use the `make` targets.
   - `search build [--strategy <name>]` reads the vault once and runs `build` on the enabled strategies, or only the named one.
   - `search query "<text>" [--strategy <name>] [--path <prefix>] [--limit <n>]` runs `search` on the named strategy, or the first enabled strategy that implements it. Output is plain lines: `path | description | score`. Exit code is non-zero on errors, zero with empty output when there are no hits.

- `search list [--strategy <name>] [--path <folder>] [--limit <n>]` runs `list` on the named strategy, or the first enabled strategy that implements it (`manifest`), and prints `path | description` lines in manifest order (root notes first, then one group per top-level folder). The manifest file is an artifact of the tool: this command is its only reader, and a missing file fails with a message to run `build`. `--path` takes a folder (a trailing `/` is added), and with no `--limit` every matching entry is printed.

The `Strategy` interface therefore has three capabilities, each optional except `build`: `search` (ranked retrieval), `list` (browsing). `manifest` implements `build` and `list`; `fts` implements `build` and `search`.

`vault-search.mk` wraps the commands so nobody types `pnpm` or the long `node` line; the vault's root `Makefile` pulls it in with one `include` line. Targets: `make index`, `make search q="<terms>" [path=<folder>] [limit=<n>]`, `make list [path=<folder>] [limit=<n>]`, `make test`. Its dependency rule runs `pnpm --dir <skill folder> install --frozen-lockfile` on the first use (`pnpm` is still needed once for that install), and it checks the Node version first (22.18+, 23.6+ or 24+). Query text reaches the tool through environment variables, so it is never interpreted by the shell.

Canonical invocation, from the vault root: `node --disable-warning=ExperimentalWarning .claude/skills/vault-search/src/cli.ts <command> ...`. The package also exposes it as `pnpm --dir .claude/skills/vault-search cli <command> ...` (pass `--config` there, since pnpm runs it from the package directory).

## Strategies

### manifest

`build` writes `Manifest.md` at the vault root, deterministically, as a plain listing: a `# Manifest` heading, a one-paragraph intro, then one group per top-level folder (root notes first), entries sorted by path, each entry a wikilink with title followed by the description. It carries no frontmatter and no breadcrumb, because it is an artifact of the tool and not a vault note, and so nothing in it depends on this vault's conventions or on the date. Identical input produces byte-identical output, which is what removes the merge conflicts. It has no `search`. It implements `list`, which parses the generated file, so the file stays a pure artifact of the tool: nothing else (and in particular not Claude, through MCP) reads or edits it.


### fts

The index carries an `INDEX_VERSION` stamp; when it is missing or differs from the code's constant, `build` drops and recreates the tables, so a tool update (schema, tokenizer, weights or reader changes) never leaves stale entries behind. `build` is otherwise incremental: it compares each Doc's `hash` against the stored hash, inserts new notes, updates changed ones, and deletes rows for removed notes. Storage is `.index/fts.db` with an FTS5 table over title, description, tags, headings and body. `search` uses BM25 with column weights favoring title and description, and converts the BM25 value to a positive score. User query text is escaped before it reaches `MATCH`, so FTS operators in a query cannot cause syntax errors. `pathPrefix` filters on the stored path.

### embeddings (future, not built)

Would add an `Embedder` port (local model or hosted API) and a vector table next to the FTS table, reusing the same `Doc` input and `Hit` output. Nothing in the core types needs to change. Sending note content to a hosted embedder is a data-handling decision to be made when this is picked up, since the vault holds client discovery material.

## Using it in a vault

`SKILL.md` has the setup steps for a new vault: copy the skill folder, add `.vault-search/config.json`, include `vault-search.mk` from the root `Makefile`, add the `.gitignore` lines, run `make index`. Two things to know about how the tool sits in a vault:

- `Manifest.md` is generated and gitignored, so a vault that used to track it untracks it (`git rm --cached Manifest.md`). Anyone who pulls that change loses their local copy (git deletes it when a tracked file is removed upstream), so everyone rebuilds once with `make index`.
- The skill folder holds markdown (this spec, `SKILL.md`, test fixtures, `node_modules` READMEs) that is not vault content. A vault's own scripts must exclude `.claude/`, and the tool's ignore list already does.

## Testing

Unit tests run against `test/fixtures/vault/`, never the real vault.

- VaultReader: missing frontmatter, missing description, malformed YAML, ignore list, H1 versus filename title.
- manifest: grouping and sort order, byte-identical output on a second run, no diff when nothing changed.
- fts: ranking favors title and description matches, incremental rebuild updates changed notes and removes deleted ones, path filter, hostile query strings (quotes, `AND`, `*`, unbalanced parentheses) do not throw.
- CLI: unknown strategy fails fast, empty result exits zero.

A final manual check runs `make index` and a few real queries against the vault.
